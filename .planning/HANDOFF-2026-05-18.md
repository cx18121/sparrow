## 3. Parallel-terminal: Exa bulk discovery

**Status:** scoped during the original conversation, never started.
Intended to run in a separate terminal so it doesn't compete with
frontend work in the main session.

**Goal:** add ~thousands of net-new long-tail companies to the DB —
ones that aren't in any VC portfolio. Closes the user's
"easier way to find companies (don't have to be VC-backed)" ask.

**Strategy locked (after we iterated on it):**

Two combined approaches, ranked by net-new yield:

1. **`findSimilar` from existing DB rows.** Sample ~500 verified
   companies biased toward low-coverage clusters (regional non-US,
   non-VC sources like `hn-hiring` / `thehub`). For each, Exa
   `findSimilar` → dedupe against DB by domain → ingest net-new via
   `runIngestor` with `source: exa-discovery`. Explores the
   *neighborhood* of known good companies, finds adjacent smaller
   companies that VCs missed.

2. **List-page mining via generic Exa search.** ~100 queries like
   `"AI startups to watch 2026"`, `"climate tech early stage"`,
   `"dev tool startups 2026"`. Returns curation articles. For each
   top result, fetch `/contents`, LLM-extract company names + URLs
   (Haiku 4.5, cheap), dedupe, ingest. Aggregator articles often
   surface companies *before* they show up in VC portfolios.

**Strategy NOT to use:** more topical `category=company` queries (the
current `ingest-exa-discovery.ts` pattern). Validated empirically —
overlaps too heavily with VC portfolio companies for popular topics.

**Spec for the parallel terminal:**

> Build `scripts/discover-exa-deep.ts`. Two strategies as above. Log
> net-new yield per strategy + per query so we can see which topics
> paid off. Cap total Exa spend at ~10k credits. Existing references:
> `scripts/ingest-exa-discovery.ts`, `scripts/_lib/ingestor.ts`. Don't
> reshape the pipeline — add a new script, follow the adapter pattern.

**Where to start:** read `scripts/_lib/ingestor.ts` and 2-3 existing
adapters (`ingest-exa-discovery.ts`, `ingest-yc.ts`,
`ingest-thehub.ts`) before writing anything. Use `EXA_API_KEY` from
`.env`.

**Open question:** target net-new count? We have ~12.3k verified
companies; doubling to ~25k is probably the right ambition. Above
that, marginal lead quality drops.

## 4. Admin dashboard

**Status:** scoped, deferred. The current motivation is
self-administration (Charlie giving specific users more send limits;
tracking own usage). Not multi-tenant admin.

**Two layers (independent):**

1. **Usage tracking** (more valuable, simpler):
   - Per-user counts for drafts generated, emails sent today/month,
     Apollo credits used (via `DailyQuota` table), Exa credits used.
   - Last active, Gmail connected, current sending limit, campaigns
     count.
   - Read-only dashboard. ~1-2 days.

2. **Per-user send-limit override** (more involved):
   - Today `normalizeSendingLimits` hardcodes `maxDaily: 500`. Admin
     needs to push individual users past that.
   - Requires `role: 'admin' | 'user'` column on `Profile` (or
     wherever — check `server/lib/user.ts`), middleware to gate
     `/admin/*` routes, and a decision on whether override locks the
     user out of self-editing.
   - ~2-3 days.

**Where to start:**

- Add `role` enum to a new column on the user/profile table. There's
  no canonical user-profile table; `user_profiles` in Supabase (the
  one `parseWorkspaceConfig` reads) is the right place.
- Seed yourself as admin via a one-off SQL.
- New route `/admin` gated by middleware. Page reads aggregate
  Prisma queries (no new APIs needed for usage tracking).
- Override field lives at the user/profile level, not in
  `workspace_config` (so user can't self-edit it).

**Decision still open:** when admin sets `dailyMaxOverride: 1000` on
a user, does the existing `normalizeSendingLimits` cap of 500 ignore
the override, or is the override applied AFTER normalization? I'd
go after — override is the source of truth when present.
